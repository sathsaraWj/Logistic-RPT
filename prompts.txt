# Hermes-RPT Development Prompts

## Prompt 0 — Create the Master Project Plan

You are the lead AI platform architect and machine-learning engineer for a new project named **Hermes-RPT**.

Hermes-RPT will be a secure, multi-tenant Relational Pretrained Transformer platform for Hermes VMS. It must learn from structured fleet, logistics and operational data.

Each Hermes customer may connect a completely different database:

* Different database engines.
* Different table names.
* Different column names.
* Different relationships.
* Different data quality.
* Different business terminology.
* Different available historical records.

The platform must ensure that a customer can access only their own database, mappings, datasets, features, model adaptations, predictions, logs and reports.

Before writing application code:

1. Analyse the complete requirement.
2. Write an implementation plan in `docs/IMPLEMENTATION_PLAN.md`.
3. Write an architecture document in `docs/ARCHITECTURE.md`.
4. Write a threat model in `docs/THREAT_MODEL.md`.
5. Write an initial relational-model research plan in `docs/MODEL_RESEARCH_PLAN.md`.
6. Write architectural decision records under `docs/adr/`.
7. Create a phased task checklist in `TASKS.md`.

The architecture must include:

* Tenant service.
* Identity and access service.
* Customer database connector service.
* Secret-provider abstraction.
* Schema discovery service.
* Schema mapping service.
* Canonical Hermes ontology.
* Feature extraction service.
* Dataset builder.
* Baseline models.
* Relational Transformer.
* Training pipeline.
* Inference service.
* Model registry.
* Prediction audit service.
* Schema-drift detection.
* Data-drift and model-performance monitoring.

Security invariants:

* Never accept `tenant_id` as an authoritative value from an editable request body.
* Resolve the tenant from a verified authentication token or trusted service identity.
* Never expose raw database passwords through an API.
* Never log secrets.
* Never allow unrestricted model-generated SQL.
* Never reuse one tenant’s connection pool for another tenant.
* Never place records from separate tenants into the same cache key, dataset or prediction request.
* Never train a shared model on customer data without explicit permission represented in the platform.
* Customer database connections must be read-only.
* All access must be auditable.
* Deny access when tenant context is missing or inconsistent.
* Fail closed rather than guessing when schemas change.

Do not implement everything in this prompt. Produce the plans and repository design first.

At the end:

* Show the proposed repository structure.
* List unresolved architectural assumptions.
* Recommend the smallest viable first prediction task.
* Run documentation checks where available.
* Do not claim implementation is complete.

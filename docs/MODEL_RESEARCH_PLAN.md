# Hermes-RPT Model Research Plan

Status: **Draft — research direction for Phases 6–12. No model code exists yet.**

## 1. Research questions

1. Can a single canonical ontology absorb enough heterogeneity across customer schemas
   (different engines, table/column names, relationships, data quality, terminology, history
   depth) that the *same* modelling pipeline works for every tenant without customer-specific
   code?
2. For the first prediction task (delivery-delay risk, see IMPLEMENTATION_PLAN.md §4), does
   modelling a target record *together with its related-record context* (a relational
   transformer) outperform a strong flat-feature tabular baseline, and by how much, once
   compute cost is accounted for?
3. Does relational self-supervised pretraining (Phase 12) improve downstream delay-prediction
   performance over training the same architecture from scratch, given only synthetic data at
   this stage?
4. Can a shared base model plus a small tenant-specific adapter match or approach a
   fully-private per-tenant model, while keeping adapter weights strictly tenant-isolated?

These are genuine open questions. This plan does not assume a "yes" to (2) or (3) going in —
Phase 11 and Phase 12 both include explicit honesty requirements ("do not claim success merely
because training loss falls," "be honest when synthetic data is insufficient to demonstrate
generalisation").

## 2. Why baselines come first

Tabular baselines (logistic regression, gradient-boosted trees, a small MLP) are cheap,
well-understood, and give a defensible quality floor and a point of comparison. Per
ADR-0008, Hermes-RPT is only justified in production if it beats the strongest baseline by a
margin that matters, not merely by existing. Baselines also exercise the full feature contract,
dataset builder, MLflow tracking, and model registry before the harder relational modelling
work begins, de-risking those shared components.

## 3. Data strategy

* **No real customer data** is used in any test, notebook, or experiment in these phases.
  Synthetic Tenant Alpha and Tenant Beta datasets (Phase 9) stand in for real customers, with
  deliberately different schemas expressing the same canonical fleet/logistics concepts.
* Synthetic data explicitly includes: missing values, class imbalance, schema drift scenarios,
  and realistic-looking (but fabricated) delay patterns — because a model that only ever sees
  clean, balanced data will not tell us anything about robustness.
* Because synthetic data is generated by the same team building the model, **any positive
  result must be treated skeptically** until validated on a design partner's real (consented)
  data; this plan does not claim synthetic-only results generalize.

## 4. Evaluation methodology

* **Temporal, not random, splits.** Delay prediction is inherently time-ordered; a random split
  would leak future information into training. Train/validation/test partitions are built by
  time cutoff per Phase 9.
* **Point-in-time correctness.** A feature is only valid if it could have been computed at or
  before the stated `prediction_time`. Phase 8 and Phase 9 both carry explicit point-in-time
  correctness tests; this is treated as a correctness bug class, not a nice-to-have.
* **Metrics.** Because delay is expected to be imbalanced (most trips are on time), accuracy
  alone is explicitly disallowed as a headline metric. ROC-AUC, PR-AUC, precision/recall/F1 at a
  chosen threshold, Brier score and calibration are all tracked (Phase 10).
* **Reproducibility.** Fixed seeds, recorded code revision, dataset/feature/mapping versions,
  and training configuration are attached to every run in MLflow (Phase 10 onward).

## 5. Modelling roadmap

| Step | What | Phase |
|---|---|---|
| 1 | Feature contract for delivery-delay risk, leakage-safe | 8 |
| 2 | Baselines (logreg, GBM, small MLP) + comparison report | 10 |
| 3 | Hermes-RPT v0.1 "Tiny" — supervised only, no pretraining | 11 |
| 4 | Self-supervised relational pretraining objectives + ablation vs. step 3 | 12 |
| 5 | Tenant adapters on top of a shared base, compared against shared-only and fully-private | 14 |

Only the **Tiny** model size is trained in Phase 11; **Small** and **Base experimental** configs
are defined but intentionally left untrained until there is a reason (real multi-tenant data,
or a design partner) to justify the added compute and complexity.

## 6. Relational representation approach

A training example for the transformer is a *target record plus bounded relational context*:
vehicle history, driver history, route history, prior deliveries, maintenance events, fuel
events — each represented through entity/table-type embeddings, column embeddings, and explicit
missing-value embeddings (rather than imputed fake values), with attention masks handling
variable numbers of related records per tenant. Relationships (Trip-uses-Vehicle,
Trip-assigned-to-Driver, etc.) are embedded explicitly rather than left for the model to infer
from co-occurrence alone. Full architectural detail is written up in `docs/HERMES_RPT_0_1.md`
once Phase 11 produces it — this plan intentionally does not pre-specify tensor shapes or layer
counts before that implementation phase, to avoid the plan and the code drifting apart.

## 7. What would make us stop or change direction

* If Hermes-RPT-Tiny does not beat the strongest baseline by a meaningful margin on synthetic
  data, Phase 11's report says so plainly, and Phase 12 pretraining is still attempted (since
  pretraining, not architecture alone, may be the source of any advantage) but the roadmap is
  revisited before investing in **Small**/**Base** sizes.
* If synthetic data proves unable to distinguish baseline from transformer performance in any
  meaningful way (e.g. because the synthetic generator's delay function is too simple), that is
  reported as a limitation of the *evaluation*, not as evidence either way about the
  architecture, and is a signal to seek a real (consented) design-partner dataset before further
  model investment.

## 8. Explicit non-goals for this research plan

* Not building a general-purpose foundation model for arbitrary relational databases — scope is
  fleet/logistics via the Hermes canonical ontology.
* Not comparing against or claiming parity with any third-party "relational pretrained
  transformer" product; Hermes-RPT is named for its own architecture, not as a claim of
  equivalence to any other system (restated in Phase 18's release-readiness language).
* Not pursuing shared cross-tenant pretraining unless and until `DataUsageConsent` (Phase 2) and
  an approved shared-dataset class (Phase 12) exist and are explicitly granted.
